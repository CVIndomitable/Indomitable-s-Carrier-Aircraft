## 三、🔴 严重问题(建议尽快修复)

### S1 · `BombEntity.explode` 与 `level.explode` 造成双重实体伤害

**位置:** `src/main/java/com/indomitable/carrieraircraft/entity/BombEntity.java:266-320`

- 先遍历 `LivingEntity` 调用 `target.hurt(..., scaledDamage)`(266-305),然后又调用 `level().explode(..., BLOCK_ONLY_EXPLOSION, ..., MOB)`(308-318)。
- `BLOCK_ONLY_EXPLOSION = new SimpleExplosionDamageCalculator(true, false, ...)` 中第一个 boolean 在 1.21.1 是 `canDamageBlocks`,第二个是 `knockbackByDistance`。`getEntityDamageAmount` 默认走 vanilla `LivingEntity.hurt`,**没有**因此禁用实体伤害。
- 注释(60 行)`// 实体伤害由 explode() 里的衰减公式控制,避免双重伤害` 与实际行为矛盾——目标会被两次伤害。

**修复建议:** 要么把衰减计算移到 `ExplosionDamageCalculator` 子类里,要么去掉手动 `target.hurt` 循环并关闭爆炸的实体伤害通道。

### S2 · `FireControlSystem.settings(UUID)` 与 `settings(ServerLevel, UUID)` 语义不一致

**位置:** `src/main/java/com/indomitable/carrieraircraft/firecontrol/FireControlSystem.java:46-53`、`src/main/java/com/indomitable/carrieraircraft/entity/AircraftEntity.java:708-710`

- 两个重载行为不同:`settings(UUID)` 总返回新对象,`settings(ServerLevel, UUID)` 先查 map 再从 `SavedData.loadSettings` 装载。
- `AircraftEntity.calculateReleaseCount` 使用三元:服务端走第一个,客户端走第二个——客户端计算时永远是新建 settings(默认值),而玩家已经从 GUI 改过——**客户端计算出的弹药数量会与玩家预期不一致**。

**修复建议:** 统一到 `settings(ServerLevel, UUID)` 或删除 `settings(UUID)` 重载;客户端不应做这种决策,应由服务端单点计算。

### S3 · 静态单例在单机模式下跨存档泄漏

**位置:** `FormationManager`、`FireControlSystem`、`CameraStateTracker`、`HitNotifier`、`AircraftSpecLoader`(均位于 `src/main/java/com/indomitable/carrieraircraft/`)

- 这些都是 JVM 级 `static INSTANCE`,`ServerGameEvents.onServerStopped` 会 `clear()`,但 `clearPlayer` 依赖 `PlayerLoggedOutEvent`。
- 单机模式玩家走 `LogoutFor` / `LoginFor`,**不会触发 PlayerLoggedOutEvent**;当玩家从「世界 A」返回标题画面再进入「世界 B」时,如果服务器不重启,这些单例的 `playerAircraft / targetMap / settingsMap` 都还存在——只在打开世界 B 时才会被 `loadPlayerData` 间接覆盖。但 `formationManager.clear()` 不会在新 `ServerStarting` 时调用!

**修复建议:** 在 `ServerStartedEvent` 或自定义 WorldChange 钩子上调用 `FormationManager.clear()` / `FireControlSystem.clearAll()`。

### S4 · `ControlTerminalScreen.renderTerrain` 在 GUI 主线程做 1100+ 同步世界查询

**位置:** `src/main/java/com/indomitable/carrieraircraft/client/screen/ControlTerminalScreen.java:721-841`

- 每帧每 3 像素一次循环:对每个采样点调 `level.getHeight(...)` + `level.getBlockState(...)` + `level.getFluidState(...)`(共 ~3300 次方块/高度查询)。
- 单次查询成本虽然不高,但在 GUI render 阶段(每帧)累积,主线程停顿可达 ~5-15 ms——掉帧、可感知的卡顿。

**修复建议:** 缓存到 `NativeImage`(或 `int[]`),只在 `playerPos`、`mapScale` 显著变化或玩家移动超过 N 格时刷新;或单独 tick 节流(例如每 20 tick 一次)。

### S5 · `AircraftEntity.tickAswDetection` 对目标反复覆盖 GLOWING 效果但不清理

**位置:** `src/main/java/com/indomitable/carrieraircraft/entity/AircraftEntity.java:668-680`、`glowingTargets` 字段 110

- 每 40 tick 给范围内水下敌对生物加 `MobEffectInstance(GLOWING, 80)`,但**只在 `clearAswGlow()`(remove 时)清空本地 set,不会移除目标实体上的 GLOWING 效果**。
- 当一架反潜机被召回/销毁,目标生物会持续发光 80 tick;但**没有任何逻辑在目标离开 AABB 时移除 GLOWING**。
- 更糟:同一目标被多架反潜机覆盖时,`glowingTargets.removeIf(...)` 检查当前扫描结果是否包含;**离开 AABB 的目标根本不在扫描中**,所以也不会被移除。

**修复建议:** 在 `removeIf` 之后,对 `glowingTargets` 中当前未扫描到的 UUID 调 `serverLevel.getEntity(uuid)` 并 `removeEffect(GLOWING)`。

### S6 · `AircraftEntity.updateStateMachine` 每 40 tick 重新注册飞机到 FormationManager

**位置:** `src/main/java/com/indomitable/carrieraircraft/entity/AircraftEntity.java:265-268`

```java
if (tickCount % 40 == 0 && level() instanceof ServerLevel serverLevel) {
    FormationManager.getInstance().registerAircraft(ownerUUID, this);
    FormationManager.getInstance().updateLeaderChunkLoading(serverLevel, ownerUUID);
}
```

- 注释(`FormationManager.java:365`)写「在线飞机每 40 tick 会自动重新注册,不会因此失联」,但 `registerAircraft` 内部还会 `putIfAbsent(leaderAircraft, ...)`,且 `updateLeaderChunkLoading` 也会调 `getLeader`——每 40 tick 强制重新解析 leader,可能在飞机死亡/被 unload 后又重新登记一个不存在的 UUID。

**修复建议:** 改为 `create()` 时一次性注册,只在 `remove()` 时注销。`updateLeaderChunkLoading` 改成由 FormationManager 自己定期 tick。

### S8 · `AircraftSpec` 是数据驱动但内置常量被 `load()` 兜底

**位置:** `src/main/java/com/indomitable/carrieraircraft/aircraft/AircraftSpec.java:153-172`、`src/main/java/com/indomitable/carrieraircraft/entity/AircraftEntity.java:982-987`
